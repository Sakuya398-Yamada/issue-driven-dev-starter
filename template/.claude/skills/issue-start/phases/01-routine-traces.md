# Phase 1 補助: 無人実装が残したもの（Issue ブランチと `needs-decision`）の扱い

`phases/01-issue-analysis.md` から読む。手順 2 でリモートに `*/#<番号>-*` のブランチが見つかったときと、「不足時の対応」で `needs-decision` の Issue の決定を得たときに使う。Phase 1 の本体が Bash の出力上限を超えないよう、条件付きのこの手順を分けてある。

## リモートに Issue ブランチがあるとき

Issue ブランチ（`<type>/#<番号>-...`）は、対話の `/issue-start` なら Phase 7 で、日次の無人実装（`.claude/routines/weekday-issue-start.md`。任意の機能）なら Phase 2 のブランチ作成で push される。PR が無いのにブランチだけがあるのは、無人実装が実装中（実行を始めてから PR を作るまで）か、途中で落ちた実行・過去の試行の残り。

ブランチ名を添えて、続けて着手してよいかユーザーに確認する（無人実装を使っているなら、その実行中に続けると同じ Issue に PR が 2 本できることも添える）。続けるなら、そのブランチは再利用せず、`phases/01-existing-pr-branch.md`「オープンな旧 PR／既存ブランチがある場合」の作り直しと同じく、別名（`-v2` 等）で切る。無人実装の実行中かどうかはこちらから見分けられず、再利用すると、同じブランチに 2 つのセッションが push することがあるため。

## `needs-decision` の Issue で決定を得たとき

ラベル `needs-decision` は、無人実装が要件の分岐を決められずに付けたもの（決められなかった点は、Issue のフッター `_スケジュール実行（weekday-issue-start）による無人実装_` の付いたコメントにある）。付いている間は無人実装の選定から外れ続けるので、このセッションで質問して決定を得たら、このセッションで次を行う:

1. 決定と根拠を Issue にコメントする（`add_issue_comment`。どの問いに何を決めたか、その理由）
2. `needs-decision` を外す。GitHub MCP の `issue_write`（method: `update`）の `labels` はラベル全体を置き換えるので、送る直前に取り直したラベルから `needs-decision` だけを除いた配列を渡す。`gh` なら `gh api -X DELETE repos/{owner}/{repo}/issues/<番号>/labels/needs-decision`
3. 本文の `## 未確定事項` に `[要確認]` の行が残っていれば、`[要確認]` を外して決定を書き、手順 1 のコメントへのリンクを添える書き換え案を、Phase 1.5「補完結果の確認」に含めて聞く（本文の更新はユーザーの確認を得てから）。行が残ると、ラベルを外しても、無人実装は決定待ちとして選ばない
