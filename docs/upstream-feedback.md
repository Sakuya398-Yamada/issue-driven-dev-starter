# 知見のテンプレートへの還元（upstream feedback）

このテンプレートを使ったプロジェクトで得た **ワークフロー自体への気づき** を、テンプレート（このリポジトリ）に還元するための仕組みの解説。

## なぜ必要か

テンプレートをコピーした時点で、利用プロジェクトのワークフローはテンプレートから切り離される。利用プロジェクト側の知見ボード（`meta: ワークフロー改善の知見ボード`）に気づきが溜まっても、それはそのプロジェクト内で閉じ、テンプレートには戻ってこない。結果として：

- 同じ非効率を、テンプレートを使う次のプロジェクトでもう一度踏む
- テンプレート側の改善は、テンプレート作者が自分で気づいた範囲に限られる

そこで、利用プロジェクトの `/issue-start` Phase 8 に「テンプレート元への還元」ステップを組み込み、**テンプレート汎用の気づきだけ** をこのリポジトリの知見ボードに流す。

## 全体像

```
利用プロジェクトA                          issue-driven-dev-starter（このリポジトリ）
────────────────                          ──────────────────────────────────
/issue-start #N
  Phase 8 手順5: 知見ボードへ追記
     └ 還元先: プロジェクト固有 ──→ ここで完結
     └ 還元先: テンプレート汎用
  Phase 8 手順6: 抽象化 → ユーザー確認 ──→ 知見ボード #3 にコメント
                                             │
                                             ▼ 棚卸し（ユーザー）
                                          改善Issue に昇格 → /issue-start で
                                          template/ と template-copilot/ を修正
                                             │
利用プロジェクトB（新規）◀─── コピー ────────┘
利用プロジェクトA ◀── テンプレート更新の取り込み（後述）
```

## 利用プロジェクト側の動き

### 1. 判定（Phase 8 手順 5）

知見ボードに書く各気づきに `**還元先**: プロジェクト固有 / テンプレート汎用` を付ける。判定基準は `.claude/rules/workflow-feedback.md`（Copilot 版は `workflow-feedback.instructions.md`）の「還元する / しないの判定」表。一言でいうと **「テンプレートを新規に使う別プロジェクトでも同じ問題が起きるか」**。

| テンプレート汎用（還元する） | プロジェクト固有（還元しない） |
|---------------------------|----------------------------|
| `/issue-start` の手順・Phase 構成・確認の粒度 | `tech-stack` / `coding-standards` の中身 |
| 汎用 rules（git-conventions 等）の規約そのもの | プロジェクト固有の MCP 構成・権限設定 |
| hooks / agents / CI の挙動・判定ロジック | 特定言語・フレームワークに閉じたハマりどころ |
| Issueテンプレート・セットアップ手順の不備 | チーム運用の都合による独自ルール |

### 2. 抽象化と確認（Phase 8 手順 6）

テンプレート元は公開リポジトリなので、還元コメントには **プロジェクト固有情報を含めない**：

- コード断片・ファイルパス・内部識別子・URL
- 顧客名・社内システム名・人名
- 認証情報・環境変数の値
- 非公開プロジェクトならリポジトリ名も書かず「非公開プロジェクト」とする

抽象化後の本文を提示し、**ローカル知見ボードへの承認とは別に** Y/E/N 確認を取る。無人還元はしない。

### 3. 投稿

承認後、GitHub MCP の `add_issue_comment`（`owner` / `repo` をテンプレート元にする）または `gh issue comment 3 -R Sakuya398-Yamada/issue-driven-dev-starter --body-file <tmp>` で知見ボード #3 に追記する。権限が無い・失敗した場合は本文をユーザーに提示して手動投稿を案内し、フローは止めない。

投稿できたら、ローカル知見ボードの元コメントの `還元先` を `テンプレート汎用（↗ 還元済み: <URL>）` に編集して、二重還元を防ぐ。

### 還元コメントのフォーマット

```markdown
## テンプレートへの知見還元 [<還元元プロジェクト>]
**還元元**: <owner/repo または「非公開プロジェクト」>／ Claude Code 版 ／ 取り込み元コミット `abc1234`
**発生Phase**: Phase N

**気づき**: ...

**現状の動作**: テンプレートの現在の手順・規約ではどう進むか

**改善案**: テンプレートのどのファイルをどう変えるか

**重要度**: Low / Medium / High

- [ ] 昇格済み
```

コメント 1 本に収まらない大きめの提案は、このリポジトリの Issue テンプレート **「テンプレートへの知見還元」**（`.github/ISSUE_TEMPLATE/template-feedback.md`）で独立 Issue として起票してもよい。

## テンプレート側（このリポジトリ）の動き

1. 知見ボード #3 に還元コメントが溜まる（このリポジトリ自身の開発で得た気づきと同居する）
2. ユーザーが棚卸しし、独立した改善 Issue に昇格させる。元コメントの `- [ ] 昇格済み` にチェックを付けて `✅ Issue #<番号> で対応` を添える
3. 改善 Issue を `/issue-start` で実装する。**`template/` と `template-copilot/` の両方** に反映し、README / docs を追従する
4. マージ後、新規プロジェクトはコピー時点で改善済みのテンプレートを受け取る。既存プロジェクトは次節の手順で取り込む

## 既存プロジェクトへのテンプレート更新の取り込み（逆方向）

還元ループは、テンプレート側の改善が既存プロジェクトにも戻ってこそ閉じる。テンプレートには更新機構を持たせていない（利用プロジェクト側でファイルをカスタマイズしている前提のため）ので、差分を見ながら手で取り込む：

```bash
# 利用プロジェクトで記録しておいた「取り込み元コミット」（workflow-feedback.md 参照）
OLD=abc1234

git clone https://github.com/Sakuya398-Yamada/issue-driven-dev-starter.git /tmp/starter
cd /tmp/starter

# テンプレートが前回コピー以降にどう変わったかを確認する
git diff "$OLD"..HEAD -- template/

# 自プロジェクトに手で反映する（tech-stack / coding-standards 等のカスタマイズ済みファイルは上書きしない）
# 反映後、workflow-feedback.md の「取り込み元コミット」を新しいハッシュに更新する
git rev-parse --short HEAD
```

Claude Code に「`/tmp/starter` の `git diff $OLD..HEAD -- template/` を読んで、このプロジェクトの `.claude/` にカスタマイズを壊さず反映して」と頼んでもよい。

## フォークして独自テンプレートにする場合

自分のチーム用にこのリポジトリをフォークしてテンプレートを育てる場合は、還元先をフォーク側に向ける：

1. フォークに `meta` ラベルと知見ボード Issue を作る（README クイックスタート手順 3〜4 と同じ）
2. `template/.claude/rules/workflow-feedback.md` と `template-copilot/.github/instructions/workflow-feedback.instructions.md` の「テンプレート元の情報」（リポジトリ・知見ボード Issue 番号）をフォーク側に書き換える
3. `.github/ISSUE_TEMPLATE/config.yml` の contact_links の URL も書き換える

フォーク側で溜まった汎用の知見を、さらに上流（このリポジトリ）に還元してもらえると嬉しい。

## 設計上の判断

- **常時Open Issue へのコメント方式**を採った理由: 利用プロジェクト側の知見ボードと同じ操作（`add_issue_comment` の宛先を変えるだけ）で済み、Claude / Copilot どちらの版でも追加のツールが不要。Issue 乱立も避けられる
- **無人投稿をしない**理由: 還元先は公開リポジトリで、投稿内容にプロジェクト固有情報が混ざるリスクがある。抽象化後の本文を人間が必ず一度読む
- **自動同期機構（git subtree / スクリプト）を持たない**理由: 利用プロジェクトはテンプレートを必ずカスタマイズしており、機械的な上書きは事故の元。差分レビュー＋手動反映を明示的な手順として置くに留めた
